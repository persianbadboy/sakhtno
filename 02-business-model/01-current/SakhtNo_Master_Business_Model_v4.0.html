1. هدف و دامنه

این سند معماری اقتصادی ساخت‌نو را تعریف می‌کند: برای چه بازیگرانی چه ارزش اقتصادی ایجاد می‌شود، Payer واقعی کیست، ارزش در کدام Route و توسط کدام Business Value Engine شکل می‌گیرد، درآمد و هزینه چگونه به هم متصل می‌شوند، چه ریسک‌هایی ایجاد می‌شود و چه Evidenceای پیش از Scale لازم است.

قیمت، Take Rate، CAC/LTV، Finance Attach Rate، LTV/Haircut، Approval Rate و Forecast عددی در این سند تثبیت نمی‌شوند و در Financial Model یا اسناد تخصصی پایین‌دستی تعیین و آزمون می‌شوند.

2. تز اصلی مدل کسب‌وکار

ساخت‌نو یک پلتفرم چندوجهی اکوسیستم ساخت است که بر فعالیت اقتصادی واقعی بنا می‌شود و از طریق چهار موتورِ تجارت، اجرا و خدمات، اعتماد و اطلاعات، و تسهیل تأمین مالی، در چهار Route اقتصادیِ تأمین و مصرف، تجارت و سرمایه در گردش، پروژه و توسعه، و ملک و دارایی ارزش ایجاد می‌کند.

ساخت‌نو بخشی از این ارزش را از طریق درآمدهای معاملاتی، خدماتی، پلتفرمی و خدمات مجاز مرتبط با تأمین مالی دریافت می‌کند، بدون آنکه به‌صورت پیش‌فرض نقش بانک، نهاد تصمیم‌گیر اعتباری، پذیرنده وثیقه، ارزیاب رسمی یا مالک ریسک اعتباری را بر عهده بگیرد.

اصل مرکزی: تأمین مالی موتور مهم رشد و تبدیل در ساخت‌نو است، اما اقتصاد پایه پلتفرم نباید برای موجودیت خود به تأمین مالی وابسته باشد.

3. مسئله اقتصادی و واحد بنیادی خلق ارزش

مسئله اصلی صنعت ساخت گسست میان تقاضا، عرضه، قرارداد، اجرا، اطلاعات، پرداخت و سرمایه است. این گسست هزینه جست‌وجو و هماهنگی، عدم تقارن اطلاعات، تأخیر، ریسک تعهدات و محدودیت دسترسی به سرمایه را افزایش می‌دهد.

واحد بنیادی Business Model، فعالیت اقتصادی واقعی و قابل شناسایی است؛ نه User Account، Lead، Listing، Loan Application یا GMV.

Need → Market → Transaction → Execution → Evidence → Payment / Settlement → Outcome

4. معماری بازیگران و Payer Architecture

User، Customer، Buyer، Seller/Provider، Beneficiary، Economic Buyer، Payer، Financial Applicant و Financial Provider مفاهیم مستقل‌اند. Revenue Model بر Payer واقعی طراحی می‌شود، نه صرفاً Beneficiary.

Payer → Economic Benefit → Charging Event → Pricing Basis → Incremental Cost → Regulatory Status

اگر یک Revenue Stream نتواند این شش جزء را مشخص کند، Revenue Model تأییدشده نیست و Hypothesis باقی می‌ماند.

6. R4 و Route Boundary

R4 از نظر Business Architecture مستقل است؛ اما تبدیل آن به P&L یا Business Unit مستقل باید با Transaction Volume، Revenue Pool، Retention، Cost-to-Serve و Cross-route Contribution اثبات شود.

Property as Transaction Object → R4. Property as Project Context → R3 + R4 Context. Property as Collateral → Primary Route مربوطه + Security/Collateral Capability.

Scope Guardrail: وجود R4 مجوز ورود ساخت‌نو به Property Listing عمومی نیست. Listing فقط زمانی توجیه دارد که مزیت تخصصی ساخت‌نو در اتصال Asset ↔ Project ↔ Evidence ↔ Transaction ↔ Finance را تقویت کند.

7. مدل چندجریانی فعالیت اقتصادی — Multi-Flow Economic Model

در هر Transaction حداقل چهار جریان مستقل ولی متصل وجود دارد و ارزش ساخت‌نو در اتصال، ردیابی و هماهنگ‌سازی آنها شکل می‌گیرد.

Flowتعریف
Physical / Service / Execution Flowحرکت کالا، خدمت، ظرفیت اجرایی، لجستیک، نصب، کار انجام‌شده، تحویل و پذیرش.
Money / Financial Flowمنبع پول، پرداخت‌کننده، Beneficiary، تأمین‌کننده مالی، پرداخت، بازپرداخت، تسویه و Reconciliation.
Data / Evidence Flowداده، سند، رویداد، Provenance، Verification، Evidence، تصمیم پشتیبانی‌شده و Audit Trail.
Rights / Obligations Flowسفارش، قرارداد، مالکیت، تعهد، مطالبه، حق دریافت وجه، پذیرش، ضمانت، انتقال یا محدودیت حق.

Identity + Authority + Transaction Context لایه مشترک روی چهار Flow هستند.

Economic Event → Obligation → Execution → Data Capture → Evidence → Entitlement / Eligibility → Money Movement → Settlement → Outcome

اصل اتصال: ساخت‌نو باید بتواند پاسخ دهد: «این پول بابت کدام تعهد، بر اساس کدام اجرای واقعی و با اتکای به کدام Evidence پرداخت شد؟»

8. R1 — Flow Model

Flowمسیر
Goods / ServiceSupplier / Service Provider → Fulfillment → Buyer؛ Order → Dispatch/Service → Delivery/Completion → Acceptance
MoneyBuyer یا Financial Provider → Verified Beneficiary → Supplier/Service Provider → Settlement
Data / EvidenceNeed → Quote → Order → Shipment/Service → Delivery → Acceptance → Payment Evidence
Rights / ObligationsOrder → Supplier obligation → Delivery/Service obligation → Buyer acceptance/claim → Settlement

Need → Match → Order → Fulfillment → Delivery / Service → Acceptance → Payment → Settlement

Finance در صورت نیاز Overlay است و Route را تغییر نمی‌دهد. Transaction Fee فقط به Charging Event قراردادی روشن مانند confirmed order، accepted delivery یا completed service متصل می‌شود؛ Lead به‌تنهایی Revenue Event نیست.

9. R2 — Flow Model

Flowمسیر
Goods / InventorySupplier → Shipment/Warehouse → Business Buyer / downstream trade
MoneyBuyer → Supplier؛ یا Financial Provider → Supplier و Buyer → Provider؛ یا financing against receivable
Data / EvidencePO → Invoice → Inventory/Shipment → Delivery → Receivable → Payment
Rights / ObligationsPO/Contract → Invoice obligation → Delivery → Receivable/Claim → Assignment/Finance if applicable → Settlement

PO → Trade → Delivery → Invoice / Receivable → Finance (optional) → Collection → Settlement → Repeat

تمایز R2 با R1 از Customer Type نمی‌آید؛ از چرخه تجاری تکرارشونده، Working Capital، Inventory/Receivable و Source of Repayment ناشی می‌شود. Receivable، Assignment، prior financing و duplicate financing باید قابل ردیابی باشند.

10. R3 — Flow Model

در R3 واحد درست‌تر Resource & Execution Flow است، زیرا کالا، تجهیزات، پیمانکار و خدمات تخصصی هم‌زمان وارد Project می‌شوند.

Flowمسیر

MoneyOwner Equity / Financial Provider / Project Cash → Verified Supplier/Contractor/Service Beneficiary
Data / EvidenceContract/Baseline → Procurement → Delivery → Progress → QC/Inspection → Certificate → Payment
Rights / ObligationsProject Contract → Work Package obligation → Performance → Entitlement/Certified Claim → Payment/Settlement

Contract → Work Package → Execution → Progress Evidence → QC / Certificate → Payment Entitlement → Controlled Payment → Settlement

Evidence of accepted/certified progress باید به Payment Entitlement و Financial Context متصل شود، بدون آنکه ساخت‌نو جایگزین Engineer، Inspector، Employer یا Financial Provider دارای اختیار شود.

13. Flow-to-Revenue & Settlement Logic

Revenue Architecture باید به Flow Event مشخص متصل شود. Revenue نباید مستقل از Transaction/Execution/Evidence/Settlement reality تعریف شود.

16. Need-first، Marketplace و Liquidity

ورودی تجاری ساخت‌نو باید مسئله کاربر باشد، نه Route یا Product. Need-first امکان Structuring، Route Classification و Matching به Market، Services و Finance را فراهم می‌کند.

Marketplace شامل Goods و Services است و به Construction Network متصل می‌شود؛ اما Marketplace نه Route است و نه کل ساخت‌نو. Transaction می‌تواند داخل یا خارج Marketplace شکل گرفته باشد.

Network Size با Market Liquidity برابر نیست. Liquidity باید در ابعاد Category، Geography، Capacity و Finance سنجیده شود. Beachhead دقیق در MVP/GTM بر اساس Demand قابل تمرکز، Supply قابل سازمان‌دهی، Pain شدید و Transaction قابل مشاهده تعیین می‌شود.

17. Revenue Architecture

چهار خانواده Revenue عبارت‌اند از Transaction Revenue، Service Revenue، Platform/Subscription Revenue و Financial Enablement Revenue. هر Revenue باید به Payer، Benefit و Value Event قابل شناسایی متصل باشد.

  1. Core Value Revenue — ارزش مستقل از Finance
  2. Transaction Revenue — معامله/اجرای موفق
  3. Service Revenue — Deliverable مشخص
  4. Platform Revenue — Capability مستمر
  5. Financial Enablement Revenue — لایه افزایشی، مشروط به قانون و قرارداد

Data Monetization در v4.0 Core Revenue نیست. Advertising/Sponsored Placement Core Revenue نیست و نباید Qualification یا Risk Ranking را مخدوش کند. Principal Trading/Merchant-of-Record نقش پیش‌فرض ساخت‌نو نیست و نیازمند Decision مستقل است.

18. Pricing، Subscription و Subsidy

Take Rate واحد برای همه Routeها معتبر نیست. Pricing بر Route × Transaction Type × Payer × Service Level بنا می‌شود. Subscription فقط در صورت Recurring Value + Recurring Usage + Recurring Capability/Cost معتبر است.

هر Subsidy باید Purpose، Target Side، Amount/Duration، Expected Behavioral Change و Exit Condition داشته باشد. Subsidy بدون Exit Condition Normal Pricing یا Unit Economics سالم تلقی نمی‌شود.

19. Finance Enablement و Multi-provider

Finance Capability/Engine است، نه Route. Need مالی از Context فعالیت واقعی استخراج و با Product Catalog مستقل و Provider مناسب Match می‌شود.

Economic Context → Financial Need → Eligibility Context → Product Matching → Provider Decision → Purpose-linked Execution

Official Credit Score، SakhtNo Risk Intelligence و Financial Provider Credit Decision مستقل‌اند. ساخت‌نو ارزش خود برای Provider را در Origination Support، Decision-support Context و Execution/Servicing Support تعریف می‌کند، نه صرفاً Lead.

Finance Stress Rule: Commerce Economics without Finance باید جدا از Incremental Economics with Finance قابل مشاهده باشد.

20. Risk، Evidence و Security Economics

هر Revenue جدید همراه با Credit، Fraud، Operational، Fulfillment، Quality، Payment، Legal، Reputation و Data Risk بررسی می‌شود. در Baseline ساخت‌نو بدون Decision مستقل وارد Principal Credit Risk، Balance-sheet Lending یا Guarantee Exposure نمی‌شود.

Evidence Depth باید متناسب با Value-at-Risk باشد. Evidence بهتر می‌تواند Verification Cost، Fraud، Dispute و Information Asymmetry را کاهش دهد، اما Evidence خود Cost دارد.

Security/Collateral Intelligence از شناسایی Candidate، ساختاردهی اطلاعات، Collateral Gap، آماده‌سازی پرونده و Provider Matching ارزش می‌سازد؛ پذیرش وثیقه، ارزیابی رسمی، ثبت/توثیق، آزادسازی و Enforcement نزد Actor دارای صلاحیت باقی می‌ماند.

21. Cost Architecture و Unit Economics

Cost Architecture شامل Technology & Infrastructure، Network Acquisition & Market Development، Operations & Transaction Support، Risk/Compliance/Verification و Partner/Financial/Service Integration است.

Cost-to-Serve باید به Flow متصل شود: حمل/خدمت به Execution Flow، پرداخت/تسویه به Money Flow، Verification/Data به Evidence Flow و Contract/Claim handling به Rights & Obligations Flow.

واحد Economics: R1 = Completed Order/Service Case؛ R2 = Completed Trade و Business cohort؛ R3 = Project/Contract/Work Package cohort؛ R4 = Completed Asset Transaction/Active Asset Case.

Contribution Margin = Net Revenue − Variable Transaction & Service Costs − Attributable Risk / Finance Costs

GMV جای Contribution Margin نیست و Shared Core نباید Route-level losses را پنهان کند.

22. Working Capital و Partner Economics

حتی اگر ساخت‌نو Lender یا Merchant Principal نباشد، اختلاف زمانی Collection، Partner Payment، Refund، Settlement و Reconciliation می‌تواند Exposure نقدینگی ایجاد کند. Financial Model باید Cash Conversion و نقش واقعی ساخت‌نو را مدل کند.

برای هر Partner باید Value Received، Value Provided، Fee/Revenue Share/Cost، SLA، Risk Ownership و Concentration/Switching Risk روشن باشد. Provider Abstraction باید معماری را از API یا Policy یک بانک مستقل نگه دارد.

23. Network Effects و Moat

Network Effectهای بالقوه شامل Marketplace، Data، Service و Finance هستند. Data quantity بدون quality/provenance و Network size بدون liquidity، Network Effect محسوب نمی‌شود.

Moat بالقوه از Construction-specific Transaction Graph، Longitudinal Performance Data، Network Relationships، Execution Evidence، Financial Connectivity، Workflow Embeddedness و Cross-route Context ساخته می‌شود؛ هیچ‌کدام به‌تنهایی Moat قطعی نیست.

24. Growth، KPI و Stage Gates

Growth Loops شامل Demand Loop، Supply Loop، Data Loop و Finance Loop هستند.

North Star پیشنهادی: Verified Economic Activity Successfully Completed through SakhtNo.

Guardrails: Completion Rate، Contribution Margin، Cost-to-Serve، Repeat/Retention، Dispute Rate، Fraud/Risk Performance، Finance performance فقط برای eligible cases، Operational Capacity و Settlement Reliability.

Scale هر Route بر Liquidity، Conversion، Completion، Repeat، Contribution، Risk و Operational Capacity واقعی متکی است. Baseline حداقل ۹۰ روز داده معتبر عملیاتی حفظ می‌شود؛ R3/R4 ممکن است Window طولانی‌تری نیاز داشته باشند.

26. مرز Business Model، Legal Mapping و Financial Model

Business Model: Who / Why / Where economics happens — Actor، Value، Payer، Revenue Mechanism، Cost Driver، Risk Owner، Unit، Route/Network Economics و Pricing Logic.

SN-LEG-001: What is executable and by whom — Legal Basis، Regulator، Authorized Actor، Permission، Official System/API، Consent/Data Requirement، Constraint، Gap و Activation Condition.

Business Model defines the economic equation. Financial Model populates and tests the equation.
